# B3 (BuildBrickBlocks) — Design

Date: 2026-10-14
Status: draft, awaiting review

## 1. Purpose

LEGO SPIKE word-block programming is popular, but the official Raspberry Pi Build HAT
can only be programmed in Python or .NET. If LEGO retires SPIKE and hubs become
unavailable, the community will still own Powered Up compatible motors and sensors,
and Build HATs will still be available.

B3 is a community, open-source (AGPL-3.0) web-based block editor for the Build HAT
that offers the same blocks and behaviour as SPIKE word blocks, limited to what the
Build HAT hardware can do:

- 4 device ports (A–D), no hub sensors (no gyro, no hub buttons), no addressable
  hub LEDs / light matrix.
- Sound goes to the Raspberry Pi audio output (3.5 mm jack, USB audio, HDMI or
  Bluetooth — configurable, since Pi Zero 2 W and Pi 5 have no jack).

**Success:** a person used to SPIKE word blocks can sit down at B3 and program a
Build HAT robot without learning anything new.

**Non-goals:** pixel-identical clone of the LEGO app; any LEGO code, artwork, icons
or trademarks. Names "LEGO" and "SPIKE" are not used in the product name.

## 2. Decisions

| Topic | Decision |
|---|---|
| Editor base | Fork of `scratchfoundation/scratch-editor` monorepo (AGPL-3.0) |
| Where programs run | Phase 1: VM in the browser. Phase 2: same VM headless in Node.js on the Pi. Hardware API is identical in both phases. |
| Hardware access | One Python daemon `hatd` on the Pi, sole owner of the Build HAT |
| Projects | Stored on the Pi + export/import of project files |
| Multi-user | PIN to connect; exactly one browser has control at a time |
| UI language | English only |
| Supported Pi | Any 40-pin Pi supported by the `buildhat` library (Pi 3, 4, 5, Zero 2 W) |
| Install | One-line install script; nothing is built on the Pi |

## 3. Architecture

```
 Browser (tablet/PC)                          Raspberry Pi
┌──────────────────────────────┐          ┌──────────────────────────────────┐
│ Editor = scratch-editor fork │  HTTP    │ hatd (Python, single process)    │
│  • scratch-blocks            │◄────────►│  • serves editor build           │
│  • scratch-gui               │  REST    │  • REST: projects (.sb3 on disk) │
│    – no stage, no sprites    │          │  • WebSocket hardware API:       │
│    + port bar A–D            │ WebSocket│     commands, telemetry, events  │
│  • scratch-vm (phase 1)      │◄────────►│  • PIN + control lock            │
│    + "B3" extension          │          │  • sound → ALSA output           │
└──────────────────────────────┘          │  • buildhat lib → serial UART    │
                                           └──────────────────────────────────┘
          Phase 2: scratch-vm in Node.js on the Pi → same WebSocket API
```

### 3.1 Editor (scratch-gui fork)
- Removed: stage, sprite pane, Motion / Looks / Pen categories, sprite-related
  blocks (sensing of sprites, mouse, etc.).
- Kept unchanged: Events (broadcast), Control, Operators, Variables, My Blocks.
- Added: port bar, PIN dialog, control indicator / "Take control", project library,
  B3 block categories (section 5).
- Scratch sound blocks are redirected to play on the Pi, not in the browser.
- Category colours resemble SPIKE for familiarity; icons and artwork are our own.

### 3.2 B3 extension (in scratch-vm)
- Implements all B3 blocks by calling the `hatd` API.
- Holds block-level state (e.g. per-port default speed set by `set speed`,
  movement pair, movement speed, 1-rotation distance) and sends fully specified
  commands, so `hatd` stays stateless with respect to block semantics.
- Reads sensor values from the latest telemetry cached in the client — no
  request per read.
- Checks device type against block requirements at execution time (section 6).

### 3.3 hatd (Python daemon on the Pi)
- Python 3, asyncio, aiohttp (HTTP, REST, WebSocket in one process), `buildhat`
  library (firmware load, serial protocol; handles Pi 5 UART automatically).
- Hardware access goes through an internal `HatBackend` interface with two
  implementations: `BuildHatBackend` (real) and `SimBackend` (simulator for tests
  and development without hardware).
- Runs as a systemd service, restarted automatically on crash.
- Plays sound on the configured ALSA device.

## 4. hatd API

### 4.1 HTTP
| Endpoint | Purpose |
|---|---|
| `GET /` | Editor static build |
| `POST /api/login {pin}` | Verify PIN, set session cookie; required for all other `/api/*` |
| `GET /api/projects` | List projects (id, name, modified) |
| `GET/PUT/DELETE /api/projects/{id}` | Read / save / delete one project (`.sb3`) |
| `PUT /api/sounds/{md5}` | Upload a project sound to the Pi's sound cache |

Export/import of project files is done in the browser (download/upload of `.sb3`)
on top of these endpoints.

### 4.2 WebSocket `/api/ws` (JSON)
- **Handshake:** `hello {api_version}` both ways; mismatched major version → error
  shown in editor.
- **Request/response:** client sends `{id, cmd, args}`, server replies
  `{id, ok: true, result}` or `{id, ok: false, error: {code, message, port?}}`.
- **Commands:**
  - `motor.run_for {port, unit: degrees|seconds, value, speed}` — reply when
    finished (blocking blocks wait for it). Direction = sign of `speed`
    (positive = clockwise); the editor converts rotations to degrees.
  - `motor.start {port, speed}`, `motor.stop {port}`,
    `motor.go_to {port, position, direction: shortest|cw|ccw, speed}`.
  - `pair.run_for {left, right, unit, left_value, right_value, left_speed, right_speed}`,
    `pair.start {left, right, left_speed, right_speed}`, `pair.stop {left, right}` —
    the editor converts steering into per-wheel values; hatd runs both wheels
    concurrently (`buildhat.MotorPair` is not used: it opens its own motor objects
    on ports hatd already owns).
  - `light.set {port, brightness}` (Light 88005),
    `matrix.set {port, pixels: 9 × [color, brightness]}` (3×3 matrix),
    `sensor.lights {port, values[4]}` (Distance Sensor lights).
  - `sound.play {md5, wait}`, `sound.beep {note, duration?}`, `sound.stop`,
    `sound.volume {value}`.
  - `stop_all`, `control.claim`, `ping`.
- **Server pushes:**
  - `telemetry` at 20 Hz: per port `{type, name, ...values}` — position, speed
    (motors); color, reflection (color); distance (distance); pressed, force
    (force); tilt (WeDo tilt); distance (WeDo motion). Also `vin`.
  - `device {port, type|null}` on attach/detach.
  - `control {holder, you: bool}` on change.

### 4.3 Control and safety
- Only the controlling client may send actuating commands (motor, pair, light,
  matrix, sensor lights, sound, stop_all). Others get `not_controller`.
- `control.claim` takes control; the robot is stopped (motors, sound) and the
  previous holder is notified, so the new holder starts from a stopped robot.
- The controller sends `ping` every 1 s. No ping for 3 s → `hatd` stops all motors
  and sound and releases control.

## 5. Blocks

Block opcodes reuse SPIKE Prime's internal opcode names (`flipper*`) where the block
exists in SPIKE, so that SPIKE word-block projects could be imported later (import
itself is not in V1). New blocks use the `b3*` prefix.

Port menus offer A–D. Full block list with SPIKE opcode mapping is in Appendix A.

| Category | V1 contents |
|---|---|
| Motors | run for, go to position, start, stop, set speed, position, speed |
| Movement | move for, start moving, steer, stop moving, movement speed, movement motors, 1 rotation distance |
| Light | Distance Sensor lights; 3×3 Color Light Matrix (as in SPIKE Essential); ➕ Light 88005 brightness / off |
| Sound | play sound (until done), stop all sounds, beep, volume |
| Events | when program starts, when color, when pressed, when distance, when timer, when condition, broadcast; ➕ when WeDo tilted, ➕ when WeDo motion |
| Control | Scratch control + stop, stop other stacks |
| Sensors | color, reflected light, distance, force/pressed, timer; ➕ WeDo tilt, ➕ WeDo motion |
| Operators, Variables, My Blocks | Scratch, plus SPIKE `is between` |

➕ = not in SPIKE, designed in the same style.

Out of V1: SPIKE extensions (More Motors, More Movement, More Sensors, Music,
Display/graphs), sound effects (pitch/pan), all hub-only blocks.

### 5.1 Supported devices

| Group | Devices (Build HAT type id) | Capabilities |
|---|---|---|
| Absolute-position motors | SPIKE Medium/Large Angular 45603/45602 (48, 49), Small Angular 45607 (65), Technic Medium/Large Angular 88018/88017 (75, 76) | all motor blocks |
| Relative-encoder motors | Technic Large 88013 (46), Technic XL 88014 (47), BOOST Interactive 88008 (38) | all except `go to position` |
| Passive motors | Train Motor 88011, WeDo 2.0 Medium 45303 and similar (1, 2) | start, stop, run for seconds, speed (as power) |
| Lights | Powered Up Light 88005 (8), SPIKE 3×3 Color Light Matrix 45608 (64) | brightness; matrix pixels/patterns |
| Sensors | SPIKE Color 45605 (61), Distance 45604 (62), Force 45606 (63), BOOST Color & Distance 88007 (37), WeDo 2.0 Tilt 45305 (34), Motion 45304 (35) | see Sensors |

BOOST Color & Distance answers the same color and distance blocks as the SPIKE
Color and Distance sensors.

## 6. Error handling

| Situation | Behaviour |
|---|---|
| No device / wrong device type for a block | Block highlighted red, message e.g. "Port A: expected Color Sensor, found Medium Angular Motor"; whole program stops; `stop_all` sent |
| Device unplugged while running | Next command on that port fails as above; port bar shows empty port |
| Connection to Pi lost | Editor shows "Disconnected", stops the VM; `hatd` stops motors after 3 s without ping; editor reconnects automatically (session cookie kept, no new PIN) |
| Low supply voltage (VIN < ~7 V) | Persistent warning in port bar: "Motors need external power" |
| Wrong PIN | Error message after a 1 s delay (slows down guessing); no lockout |
| `hatd` crash | systemd restarts it |

## 7. Installation and releases

- Nothing is built on the Pi (webpack needs GBs of RAM). GitHub Actions builds the
  editor on each release and packs it with `hatd` into one release archive.
- `install.sh` (one line: `curl -sSL <url>/install.sh | bash`) on Raspberry Pi OS
  bookworm:
  1. enables UART, disables serial console (`raspi-config nonint`);
  2. installs `python3-build-hat`, `python3-aiohttp` via apt (no pip);
  3. downloads the release to `/opt/b3`, data (projects, sound cache, config) to
     `/var/lib/b3`;
  4. installs and enables a systemd service;
  5. generates a PIN and prints it with the URL (e.g. `http://<hostname>.local`);
  6. offers a reboot if UART settings changed.
- The same script updates and uninstalls.
- Configuration file: PIN, audio output device, HTTP port.

Later (not V1): `.deb` in an apt repository, ready-made SD card image, Wi-Fi hotspot
mode on the Pi for places without usable Wi-Fi.

## 8. Resource budget

- `hatd`: ~50–80 MB RAM — fine on Pi Zero 2 W (512 MB).
- Editor runs in the client browser; the Pi only serves ~10–20 MB static files.
- Phase 2 (VM in Node.js on the Pi): estimated 100–200 MB RAM; must be measured on
  Pi Zero 2 W before committing to it there.

## 9. Testing

- `hatd`: pytest against `SimBackend` — API, control lock, ping timeout, PIN,
  projects, sound cache.
- B3 extension: Jest against a mocked `hatd` client — block semantics, stored
  speed, device-type errors.
- End-to-end: Playwright — `hatd` with `SimBackend`, open editor, log in, build a
  program, run it, assert commands received.
- Hardware: tests marked `hardware`, run manually on the Pi, plus a manual checklist
  per device group.

## 10. Repository layout

The B3 repository is a fork of `scratch-editor`, so upstream changes can be merged.

```
packages/scratch-gui/        # modified: no stage, port bar, project library, control UI
packages/scratch-vm/         # modified only where needed to register the extension
packages/b3-extension/       # B3 blocks, hatd client, telemetry cache
hatd/                        # Python daemon (+ tests)
install/                     # install.sh, systemd unit, default config
.github/workflows/           # build + release
```

## 11. Phases

- **Phase 1 (V1):** everything above, VM in the browser.
- **Phase 2:** headless VM in Node.js on the Pi, program keeps running without a
  browser, optional autostart of a chosen project at boot.

### Not supported (hub-only or out of V1)

`flipperevents_whenGreaterThan` — purpose to be checked against SPIKE help before
implementation; included only if it applies to port devices.
